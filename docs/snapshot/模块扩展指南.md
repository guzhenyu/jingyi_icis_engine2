# 快照模块扩展指南

以本仓库护理记录为模板：源数据写入和快照标记在同一事务内完成，读取时按需刷新。

## 1. 术语

| 术语 | 含义 |
| --- | --- |
| `pid` / `deptId` | 患者 ID：`patient_records.id`；科室编码：`rbac_departments.dept_id`。 |
| `statistics_date` | 统计日期，只有年月日；Java `java.time.LocalDate`，数据库 `DATE`，不含时间和时区。 |
| `zoneId` | 系统配置时区：`ConfigProtoService.getConfig().getZoneId()`；不写入日快照表或 PB。 |
| 统计窗口 | `StatisticsDayWindow` 的 UTC 半开范围 `[start, end)`。护理记录用 monitoring 窗口，出入量及用药入量明细用 balance 窗口；正文与标题复用公共取窗结果。 |
| 业务源表 / 日快照 | 源表是真实来源；`patient_snapshots` 按 `(pid, statistics_date)` 一行，`payload` 为 `PatientSnapshotPB` 二进制的 Base64。行级 `last_modified_at` 记业务修改时刻，`snapshot_at` 记最近刷新时点；后者为空时刷新所有已注册模块。 |
| 模块 `lma`（last_modified_at） | PB 中 `<模块>_lma_iso8601`：实际业务变更使用的、锁内取得的服务端 UTC 修改时刻；不是记录的业务归属时间。 |
| 模块 `sa`（snapshot_at） | PB 中 `<模块>_sa_iso8601`：本模块成功刷新时点，也是持续计算的时间上限。默认 `sa` 缺失或非法、非空 `lma` 非法、或 `lma >= sa` 时刷新；成功空结果也写 `sa`。`lma/sa` 使用 UTC 秒精度，相等时保守刷新；行级时间列不代替模块刷新判断。 |
| 锁计划 | `XxxLockPlan` 汇总业务锁与受影响日快照锁，并保存复查所需的旧值；`SnapshotChangePlan.Change(pid, effectiveTime)` 用患者和时间点定位受影响统计日。 |

公共支撑：`app_transaction_locks`、`patient_snapshots`、`balance_stats_shifts`。`patient_nursing_reports` 是旧护理单缓存表；对应报表复用快照需单独接入和验收。

查询接口不保证只读，拆 Reader 时须检查完整调用链：

- 观察查询可能同步设备数据，还会联写用药入量观察记录。
- 用药查询可能生成执行记录。
- 血气查询的 `force_sync` 会导入数据；即使关闭该开关，也可能补写缺失的记录人和记录时间。
- 检验查询会补齐并保存参数元数据。
- 护嘱详情会同步并生成执行记录。

关闭同步开关不等于只读。Service 编排准备动作并标记实际源变更，Reader 只读已准备的数据；没有独立 API 的同步路径也必须覆盖。

## 3. 模块扩展规范

参照 [NursingRecordService](../../src/main/java/com/jingyicare/jingyi_icis_engine/service/nursingrecords/NursingRecordService.java) 的增删改及 `withNursingRecordLocks`、[NursingRecordLockPlan](../../src/main/java/com/jingyicare/jingyi_icis_engine/service/nursingrecords/NursingRecordLockPlan.java)、[NursingRecordSnapshotModule](../../src/main/java/com/jingyicare/jingyi_icis_engine/service/snapshots/NursingRecordSnapshotModule.java)。按需复用或补齐下列职责，保留本模块的时间精度、更新方式及接口语义。

| 位置 | 职责 |
| --- | --- |
| `service/<模块>/XxxService` | 参数、权限和业务校验；编排锁及业务表写入。 |
| `service/<模块>/XxxReader` | 按传入窗口查源表、映射现有 PB，保留已存结果，可做无副作用计算；不生成业务记录、不执行同步或写库，失败不伪装为空结果。不添加 `@Transactional`，不调用 `LockExecutor`。 |
| `service/<模块>/XxxLockPlan` | 汇总、比较锁计划，不查库。 |
| `repository/<模块>/XxxJdbc` / `XxxRepository` | 静态 JDBC 查询用于预读及锁后复查；JPA 用于普通读取和持久化。 |
| `service/snapshots/XxxSnapshotModule` | `markModified` 只写本模块 `lma`；`refresh` 通过 Reader 替换本模块数据并写 `sa`，保留 `lma`，不写源表。 |
| `service/locks/LockKeys` / `LockExecutor` | 统一资源键；在 `app_transaction_locks` 中按键排序加行锁，统一事务及重新规划。 |
| `service/snapshots/SnapshotService` | 统计日计划、刷新判断及整行保存；不添加模块专用分支。 |

每轮先约定目标、范围、文件和验收标准；设计审阅通过后实施，实现审阅通过后提交。准备改造可分轮；模块注册与写入标记一起启用：

1. **实现 Reader 与快照模块。** 在 [icis_snapshot.proto](../../src/main/proto/config/icis_snapshot.proto) 追加本模块的数据及 `lma/sa` 字段，保留已有字段号。实现 Reader，复用现有 PB、字典与转换；扩展 `SnapshotModule.Kind`，实现 `@Component XxxSnapshotModule` 并委托 Reader。

   接入快照模块不改变既有查询的数据来源。`getNursingRecord` 继续通过 Reader 实时查询业务表；快照刷新复用同一个 Reader。Reader 直接返回业务数据，不因接入快照而增加 `ReturnCode` 包装。

   Reader 注释须说明普通查询与快照刷新的调用场景，以及不添加 `@Transactional`、不调用 `LockExecutor` 的理由：Reader 只负责读取与转换，事务边界由调用方编排；快照场景沿用 `LockExecutor` 已建立的事务。

2. **业务变更的锁定与失效标记规则。** 查全可能修改源数据的 API、导入、定时任务、联写及患者合并等入口，确定源表和影响范围。查询入口中的同步或补写也须遵守这些规则；纯读取不标记失效。

   对于按单个业务时间归属的记录，新增影响新时间对应的统计日，修改影响旧、新时间对应的统计日，删除影响旧时间对应的统计日。写入前据此确定锁范围，实际修改后标记相应快照失效。

   保持公共快照框架不变。对于影响多个统计日的修改，由业务模块确定全部受影响日期，并转换成现有接口所需的 `Change` 集合。转换结果经 `planChanges` 映射后必须覆盖所有受影响日期；锁后须复查决定影响范围的业务数据。所有相关锁在写入前一次取得，源数据修改与快照失效标记在同一事务内完成。

   生成 `Change` 时须依据统计窗口，不能只取区间端点，也不能按 UTC 固定间隔 24 小时取点。`isPlanCurrent` 复查计划中患者的当前科室及传入时间点的日期映射，原记录的患者、起止时间等信息须由业务模块复查；不一致时重新生成完整计划。

3. **改造业务写入入口。** 全部锁资源可直接确定时用 `execute`；动态资源在 `executePlanned` 的 `planSupplier` 内做 JDBC 预读，由业务模块生成 `Change` 集合，调用 `SnapshotService.planChanges` 生成日计划，再组装 `XxxLockPlan`。`addxxx` 等业务入口负责定义并传入 `planSupplier`、`resourceResolver`、`validateAfterLock` 和 `businessAction`，由 `LockExecutor` 按预读计划、取得全部锁、锁后复查、执行业务的顺序调用。

   批量、联写均由外层一次收齐全部业务锁与快照锁；锁后复查记录及日计划（`isPlanCurrent`），不一致返回 `false` 重做计划，业务只用复查后的记录。预读后记录消失时沿用示例的兜底锁处理。

   模块通过 `XxxJdbc` 预读并复查业务关联键、完整患者集合及决定影响范围的字段。`isPlanCurrent` 只重算已传入患者的科室与日期映射，不能代替业务关联复查；例如检验报告关联哪些本地患者，须由检验模块自行确定和复查。

   调用 `LockExecutor` 时不能已有外层事务；它负责开启事务并取得全部锁。锁后取 `TimeUtils.getNowUtc()`，在业务回调中先修改业务表（例如向 `nursing_records` 新增护理记录），再调用 `SnapshotService.markModified(kind, snapshotPlan, changed, now)` 更新对应日快照的模块 `lma`。业务表和快照表写入使用同一个事务，一起提交或回滚；无实际变化不标记，写后失败抛异常整体回滚。联写分别标记受影响的已注册模块；锁内不补锁、不嵌套加锁、不另开连接或事务写库。

   `changed` 是本次实际修改后需要标记失效的 `Change` 集合。每个元素的患者 ID 和 `effectiveTime` 必须与 `snapshotPlan.statisticsDates` 中的某个键完全相同。注意，`effectiveTime` 不是服务端的修改时刻 `now`。

   调用 `markModified` 时必须已有事务，模块必须已注册，且 `changed` 中的每个元素都必须能在上述映射中找到，否则抛异常。锁的取得和锁后复查已经由前面的回调流程完成；`markModified` 不会检查调用方实际持有哪些锁，也不会再次加锁或执行复查。

4. **验证业务写入与快照刷新。** 用 PostgreSQL 17 / Testcontainers 验证成功空结果、跨日与移时、删除、锁计划重试、写入与刷新互斥、真实联写回滚；事务测试不套外层事务，通过服务入口及独立连接验证提交和锁等待。从事务外调用 `SnapshotService.get(pid, statDates, forceRefresh)` 验证本模块的按需刷新，并确认既有业务查询仍通过 Reader 实时取数。

危急值与 shortcuts 不在范围。不提供统计配置变更的主动失效机制；读取时发现保存的窗口与当前窗口不一致，会自动强刷对应统计日的全部已注册模块。需要立即重建时，可手工强刷受影响日。

### 3.1 护理评分接入约定

- `addpatientscore`、`updatepatientscore`、`savepatientscore` 分别执行新增、按 ID 更新、按业务键新增或覆盖。
  三个入口独立编排，复用公共校验、服务端文本生成和锁计划，不通过 `UpdateMode` 分发或 `withScoreLocks` 包装。
  三个请求均仅含字段号为 1 的 `record`，必须明确传入 `record.pid`、`record.code`、`record.recorded_at_iso8601`；
  前端缺少 `pid` 时补当前患者 ID。
- 三个写入入口统一使用当前登录用户的账号自动 ID 和服务端姓名，忽略客户端传入的记录人字段。
  前端不发送 `recorded_by`、`recorded_by_account_name`；查询响应仍返回记录人及姓名用于展示。
- 新增按 `(pid, score_group_code, effective_time)` 检查重复；保存按同一三元组定位，忽略客户端 ID。
  更新必须提供活动记录 ID，不允许修改患者或评分类型，不一致时返回 `PATIENT_SCORE_ID_NOT_MATCH`；
  缺失或非法时间报错，目标三元组被其他活动记录占用时报重复错误。
- 写入前根据评分明细重新计算总分，普通评分的提交总分须与计算值一致，否则返回 `SCORE_GROUP_SCORE_NOT_MATCH`。
  谵妄保留原有特殊校验，仍允许提交配置中的“无法评估”等未知值。
- 新增和修改的患者存在性及时间边界在评分计算、加锁前校验一次，锁后不重复业务校验。
  `PRE_ADMISSION`、`ADMITTED` 状态仅校验非空的入科时间下限；
  `PRE_DISCHARGE`、`DISCHARGED` 状态仅校验非空的出科时间上限；其他状态不使用这两个时间边界。
- 前端七个评分弹窗统一以 `YYYY-MM-DDTHH:mmZ` 提交时间，正常前端写入链路已是分钟精度。
  后端新增、修改及单条查询继续截断到分钟，评分锁按分钟取得，本次不新增含秒历史数据迁移或兼容改造。
  锁计划预读保留源记录完整时间，用于锁后复查、旧观察项锁和改时迁移；删除不修改源记录的有效时间。
- 有配置映射时，三个入口均联写观察项，评分和观察项使用同一份服务端生成文本。改时软删除旧时间的观察项，并在新时间新增或更新；观察项替换保留软删除历史，在同一事务先刷新旧行删除再插入新行，满足活动记录部分唯一索引。
- 四个入口直接使用 `LockExecutor.executePlanned`，通过 `ScoreLockPlan` 收齐所需评分锁、映射观察项锁和统计日快照锁。
  更新改时同时覆盖旧、新时间。取得全部锁后，通过 JDBC 复查按 ID 预读的源记录定位字段及快照日期计划；变化时回滚并重新规划。
  评分入口的观察项联写使用当前 JPA 事务，不经独立连接提交；评分、观察项、护理单失效更新和评分模块 `lma` 一起提交或回滚。
- 删除按 ID 定位，保留 `by_monitoring` 约定：仅为 `true` 时联删观察项；两种删除入口均锁定评分、标记评分快照并更新护理单失效时间。
  预读后被并发删除时保留原评分锁键，重试后返回成功；重复删除不重复失效。实际软删除使用锁后通过 Repository 读取的当前记录。
- 四个入口在 `executePlanned` 外捕获锁执行、联写等运行时异常，事务回滚后返回 `INTERNAL_EXCEPTION`，不提交部分联写结果。
  JSON 解析失败仍返回 `PARSE_JSON_FAILED`，业务校验错误保留各自错误码。
- `ScoreReader` 为普通评分列表和快照提供实时源表读取，沿用已存文本，不按当前配置重算历史数据。普通列表保留结束时间包含及时间降序；快照查询全部评分类型的 monitoring 半开窗口，按时间、ID 升序，源记录解码失败时刷新失败，不伪装为空结果。
- `ScoreSnapshotModule` 复用已有 `score_groups`、`score_group_lma_iso8601`、`score_group_sa_iso8601` 字段。空结果也写 `sa`；没有实际评分变化时不标记评分模块失效。改时标记旧、新时间对应的统计日，并分别失效旧、新时间的护理单。

### 3.2 随时间变化的快照字段（可选）

如果本模块的快照结果在业务表没有修改时也会随时间变化，例如未完成持续用药的累计入量，才需要在自己的 `XxxSnapshotModule` 中覆盖 `needsRefresh`。护理记录这类结果仅随业务数据修改而变化的模块，沿用默认实现即可。

以未完成的持续用药为例：假设该模块按输注速度和持续时间计算累计入量，一条记录从 08:00 开始，以 10 mL/h 持续输注，尚未结束，期间没有暂停或速度调整，以下时刻都在同一个统计窗口内：

- 10:00 刷新快照时，累计入量为 20 mL，模块 `sa` 记录为 10:00。
- 11:00 再次调用 `SnapshotService.get` 时，业务表没有变化，`lma` 未更新，但累计入量应为 30 mL。模块的 `needsRefresh` 判断该用药尚未完成且计算截止时刻已经推进，返回 `true`；随后 `refresh` 让 Reader 按本次 `Context.snapshotAt` 重新计算，并更新数据和 `sa`。

这个例子说明了为什么只比较 `lma` 和 `sa` 不够。实际累计入量仍复用已有用药计算规则。统计窗口结束后，需要将结果补算到窗口终点；补全后不再因当前时间继续推进而反复刷新该历史日，但后续业务修改仍须触发刷新。

调用 `SnapshotService.get` 时，其内部的 `getLocked` 会调用模块的 `needsRefresh(context, snapshot)`，返回 `true` 才调用该模块的 `refresh`；需要整体强刷时则直接刷新。覆盖 `needsRefresh` 时，先调用 `SnapshotModule.super.needsRefresh(context, snapshot)`：默认判断需要刷新就返回 `true`，否则再按本模块的计算规则判断时间推进是否需要重算。这个判断只在读取快照时执行，不会启动后台定时任务。

需要按时间计算的模块，在 `refresh` 中将 `Context.snapshotAt` 传入 Reader，作为本次快照计算使用的当前时刻；Reader 不重新取当前时间，计算截止不晚于所用窗口终点和该时刻。模块 `sa` 使用 `TimeUtils.toIso8601StringWithSeconds(context.snapshotAt(), "UTC")` 写入。这类模块须验证没有业务写入时仍能随时间更新、窗口结束后能补全最终结果，以及之后的业务修改仍能触发刷新。
